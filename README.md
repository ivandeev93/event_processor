# Сервис приёма и обработки событий

Небольшой backend-сервис на FastAPI для приёма webhook-событий и их асинхронной обработки через очередь задач на базе SQLite.

## Возможности

- Приём событий через `POST /webhook`.
- Защита от дублирования событий по уникальному `event_id`.
- Сохранение событий и задач в SQLite.
- Независимый worker для обработки очереди.
- Повторные попытки обработки при временных ошибках — максимум 3 попытки.
- Экспоненциальная задержка между повторными попытками.
- Разделение временных и постоянных ошибок.
- Восстановление задач после аварийного завершения worker.
- Защита от одновременного захвата одной задачи несколькими worker.
- Получение статистики через `GET /stats`.

## Установка и запуск

Клонировать репозиторий:

```bash
git clone https://github.com/ivandeev93/event_processor
cd event_processor
```

Создать виртуальное окружение:

```bash
python -m venv venv
```

Активация в Windows:

```bash
venv\Scripts\activate
```

Установка зависимостей:

```bash
pip install -r requirements.txt
```

### Запуск API

```bash
uvicorn app.main:app --reload
```

API будет доступен по адресу:

`http://127.0.0.1:8000`

Интерактивная документация Swagger:

`http://127.0.0.1:8000/docs`

### Запуск Worker

В отдельном терминале, из корневой директории проекта:

```bash
python -m app.worker
```

Worker самостоятельно опрашивает базу данных, получает доступные задачи и обрабатывает их.

## API

### POST /webhook

Принимает событие и создаёт задачу для последующей обработки.

Пример запроса:

```json
{
  "event_id": "abc-123",
  "type": "payment_succeeded",
  "payload": {
    "amount": 1500
  }
}
```

Ответ при создании нового события:

```json
{
  "event_id": "abc-123",
  "created": true
}
```

При повторной отправке события с тем же `event_id` новая запись не создаётся:

```json
{
  "event_id": "abc-123",
  "created": false
}
```

Некорректные данные отклоняются с HTTP 422.

### GET /stats

Возвращает статистику по типам событий и статусам задач.

Пример ответа:

```json
{
  "events_by_type": {
    "payment_succeeded": 5,
    "user_registered": 3
  },
  "tasks_by_status": {
    "pending": 2,
    "success": 4,
    "failed": 1,
    "skipped": 1
  }
}
```

## Обработка задач

Для каждого принятого события создаётся отдельная задача в таблице `tasks`.

Возможные статусы:

| Статус | Описание |
|---|---|
| `pending` | Ожидает обработки или повторной попытки |
| `success` | Успешно обработана |
| `failed` | Исчерпан лимит попыток |
| `skipped` | Постоянная ошибка, повторная обработка не требуется |

### Повторные попытки

При возникновении временной ошибки worker планирует повторную обработку задачи.

Максимальное количество попыток — 3.

Используется экспоненциальная задержка:

| Неудачная попытка | Задержка перед повтором |
|---|---|
| 1 | 1 секунда |
| 2 | 2 секунды |
| 3 | Повтор не выполняется, статус `failed` |

### Восстановление задач

При получении задачи worker устанавливает время блокировки `locked_until`.

Если worker аварийно завершается, после истечения блокировки задача снова становится доступной для обработки.

Если лимит попыток исчерпан, задача переводится в `failed`.

### Конкурентная обработка

Получение задачи реализовано одним условным SQL-запросом `UPDATE ... RETURNING`. SQLite сериализует операции записи, что позволяет избежать успешного захвата одной и той же задачи несколькими worker.

## Принятые технические решения и ограничения

- SQLite используется как хранилище событий и очередь задач.
- Создание события и соответствующей задачи выполняется в рамках одной транзакции.
- Доступ к данным инкапсулирован в репозиториях.
- Бизнес-логика отделена от API и работы с базой данных.
- Worker запускается независимо от FastAPI.
- Обработка имеет семантику *at-least-once*: при аварийном завершении worker после выполнения внешней операции, но до сохранения статуса `success`, задача может быть обработана повторно. Поэтому реальные внешние операции должны быть идемпотентными.
- Бизнес-обработка представлена заглушкой и предназначена для демонстрации механизма очереди.
- SQLite подходит для данного задания и небольших нагрузок. Для production-систем с высокой конкурентной нагрузкой следует рассмотреть более подходящую СУБД и дополнительные механизмы контроля выполнения задач.
